# 首版数据格式草案

与API_CONTRACT版本同步，当前0.1。A、B、C共同确认后使用。

## 厨房资源

资源字段：`id`、`type`、`capacity`。示例类型cook、burner、wok、rice_cooker。首版具体设备capacity=1，用独立ID区分两口锅。主动操作占用cook；等待阶段可仅占设备，需看管的时段拆出检查任务。锅和灶同时需要时应同时占用两个资源。

## 任务

字段：`task_id`、`dish_id`、`name`、`duration_sec`、`dependencies`、`resource_ids`。所有依赖和资源ID必须存在，任务图不能有环。`finish_window_sec`为可选的最早与最晚完成秒数，参考点为计划available_from，不得同实际熟度混淆。

首版固定资源样例用于共同测试；可选厨具、人员指派、批量备菜等在B定义字段并经共同确认后扩展，不直接将字符串名称当资源匹配。

## 实际状态

任务状态建议not_started、in_progress、paused、completed、cancelled。保存实际开始、完成、累计用时和预计剩余时长。暂停是否释放资源由任务与现场确认决定，不能默认把锅或灶释放。

已完成任务实际起止不变；进行中实际开始保留，更新预计剩余与占用；未来任务可重排。取消事件涉及后继依赖，必须重新校验。

## 计划与版本

计划包含资源、任务、available_from、serve_at、schedule_version及求解状态。事件有唯一event_id和expected_version，避免重复点击执行两次或将旧结果覆盖新结果。

## 菜谱和参考数据

真实菜谱需含食材用量、份量、来源、核对状态、任务、忌口或过敏原信息和安全提示。价格与营养记录来源和适用条件，缺少依据时保留未知，不生成精确值。容量校准与固体质量换算分开。

数据库保存用户、厨房、校准、菜单、任务、计划、事件、反馈、饮食记录和照片元数据。媒体原件不进入Git。实际表结构由A维护；共享的是初始化脚本和合成样例，不是各人的运行数据库。
